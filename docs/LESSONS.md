# Lessons from Agentic Work Infra

本文档记录协同模型和治理规范在实际使用中的失败案例。历史条目保留当时证据；未注明正式承接位置的规则仍是候选，不因出现次数或命令语气自动生效。

## 使用说明

**记录时机**：
- 发现原则或规范在实际应用中的问题
- Agent 在使用本项目指导其他项目时遇到困难
- 文档设计导致误解或低效

**审议与晋升**：
- 同一问题出现三次触发审议，单次严重问题也可审议；次数不自动决定晋升。
- 条目是候选规则与证据。人确认根因、反例、适用范围和维护成本后，通用规则晋升到 `docs/governance/templates/standards.md`，本仓特有约束更新其所属文档。
- AGENTS 保持稳定边界与路由，正式规则只维护一处。本文件保留证据及引用，不维护第二份正文。
- 来源、晋升和目标项目采用流程见 [文档工程指南](governance/agent-governance.md#规则如何演化)。

## 文档设计

### 文档结构不够清晰（必需/推荐/可选）

**规则**：必需、推荐、可选要明确区分，不能笼统要求"都要有"

- 证据1：2026-10-12 review magpie 后发现，我们对小项目要求过多文档（architecture/、product/、research/ 都要求有），导致过度设计
- Seen 1× (2026-10-12)

### 缺少 LESSONS 机制

**规则**：必须建立失败记录机制，让 Agent 从重复错误中学习

- 证据1：2026-10-12 研究 magpie，发现 LESSONS.md 是其人机协同的核心创新，但我们的体系中没有这个机制
- Seen 1× (2026-10-12)

### 验收标准不可执行

**规则**：验收标准应该分层：第一性原则 + 项目适配层，而不是抽象原则

- 证据1：2026-10-12 发现 agent-governance.md 说"代码即事实，运行结果是最终判断标准"，但 Agent 不知道具体要运行什么
- Seen 1× (2026-10-12)

### 模板职责与指南冲突

**已晋升**：[文档职责与更新条件](governance/agent-governance.md#文档职责与更新条件)。

- 证据1：2026-10-14 项目适配讨论发现，指南将 DESIGN 定义为架构概览，模板却定义为视觉规范；README 模板实际是模板使用指南。
- Seen 1× (2026-10-14)
- 审议结果：用户确认 DESIGN 是视觉规范。指南改为由独立架构文档维护职责与接口，README 模板改为项目入口。

### 稳定文档重复维护当前状态

**已晋升**：[文档职责与更新条件](governance/agent-governance.md#文档职责与更新条件) 与 [入口和路由](governance/agent-governance.md#入口和路由)。

- 证据1：2026-10-14 项目适配讨论中，用户指出 README 与多份文档频繁更新容易遗漏，要求稳定骨架后仅少量文档持续维护。
- Seen 1× (2026-10-14)
- 审议结果：指南明确每类文档的更新条件，索引只做路由，架构与入口不复制阶段摘要。

## 协同机制

### 未实测就断言环境能力

**规则**：声称"不具备某能力/环境不支持"之前，必须先在本机实测（查配置、跑命令），区分"本会话工具列表没有"和"宿主不存在"

- 证据1：2026-10-13 我断言"无浏览器/computer use 能力"，未查看任何本机配置。用户指出 Claude Code 官方支持这些能力且本机环境存在。2026-10-14 实测：playwright(chromium+系统Chrome) 均可启动、Chrome 155 在装、`--chrome` flag 存在
- Seen 1× (2026-10-13)

### gitlink 混入主仓库

**规则**：引用外部仓库用"下载快照到 gitignore 目录"或正规 submodule，不接受裸 gitlink 意外进入主仓库

- 证据1：2026-10-13 `thirdparty/magpie` 以 mode 160000 gitlink 被提交（314a0ee），后续 feb057c 删除 gitlink 时本地目录一并丢失，研究文档失去本地源码
- Seen 1× (2026-10-13)
- 做对示例：2026-10-14 经 codeload 下载快照到 `thirdparty/`（gitignore），可重下、不进主仓库

### 规则转写未溯源原始模式

**规则**：把外部项目的机制转写进本仓体系前，先对照原始项目的实际结构（源码/原文），不凭研究笔记的转述直接落规则

- 证据1：2026-10-14 用户指出 LESSONS 晋升出口写成"AGENTS.md 或项目规范"，而 magpie 实际模式是晋升到 code-standards.md、AGENTS.md 永远保持 5KB 入口不收规则。研究文档阶段就转写错了，治理文件一路继承，波及 8 处 4 类文件
- Seen 1× (2026-10-14)
- 做对示例：2026-10-14 本轮修正——先 grep 全仓找出所有错误出口，统一改为 STANDARDS.md 单一出口并注明渐进披露理由

### 敏感信息先于公开被提交进历史

**规则**：任何真实 key、凭证（哪怕是截断的尾号）不进 git 历史；公开仓库前先全历史扫描（`git log --all -p | grep` 凭证模式），未推送的历史用 filter-branch/新孤儿分支重建

- 证据1：2026-10-14 准备公开仓库时发现，2026-10-13 的 `magpie-配置记录.md`（feb057c 提交、fca761e 删文件）把完整 sorrycode key 写进了历史；所幸 57 个 commit 均未推送，origin 侧干净
- Seen 1× (2026-10-14)
- 做对示例：2026-10-14 push 前扫描发现 → filter-branch 清洗未推送历史 → gc 清残留 → 全历史复扫 0 匹配 → 才推送

### 规则过早固化

**规则**：区分"稳定原则"、"经过验证的规范"和"待验证规则"，有规则晋升机制

- 证据1：2026-10-12 发现所有原则都在 agentic-work-model.md 和 agent-governance.md 中直接固化，缺少"暂存区"，可能是基于假设而非真实失败案例
- Seen 1× (2026-10-12)
