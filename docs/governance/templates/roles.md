## 适用场景

| 判断维度 | 单 Agent | 双 Agent | 三层协作 |
|---------|---------|---------|---------|
| **决策复杂度** | 人能一次说清所有要求 | 需要先定边界再执行 | 需要维护模块间契约 |
| **并行需求** | 单线程足够 | 单线程足够 | 需要多人/多模块并行 |
| **实现周期** | 当天或次日可完成首版 | 几天内迭代可收敛 | 跨周甚至跨月推进 |
| **审查成本** | 人能快速扫一遍代码 | 人能在1小时内审查完 | 人无法详细审查所有实现 |

**协作模式**：
- **单 Agent**：你与一个 Agent 在一次对话中完成决策+实现+验证的闭环
- **双 Agent**：Architect（决策）+ Worker（实现），你直接审查
- **三层协作**：Architect + Worker(s) + Reviewer，你依赖分层判断做裁决

本文档定义三层协作架构。项目满足单/双 Agent 条件时可以简化或不使用。

## 模板部分（供项目实例化）

本项目启用多 Agent 协作。当前活跃角色：

### Architect（主架构师）

- **会话名**：`<填写会话名，如 architect-main>`
- **职责**：
  - 理解业务目标、做架构决策
  - 制定模块边界、接口契约、交接计划
  - 维护 docs/HANDOFF.md（当前状态、下一步、阻塞）
  - 制定任务包，分发给 Worker
  - 处理 Reviewer 升级的架构问题
- **只保留上下文**：目标、边界、当前状态、关键决策
- **不做**：看具体代码、做代码审查、写测试

### Worker（执行者）

- **会话名**：`<填写会话名，如 worker-模块名>`
  - 示例：worker-auth、worker-payment、worker-api
- **职责**：
  - 读取任务包：范围、契约、验收标准
  - 实现功能、写测试、自验证
  - 提交 PR 给 Reviewer
  - 根据 Reviewer 反馈修复问题
- **只关注**：当前任务的范围和契约
- **不做**：跨模块决策、架构调整、查看其他模块实现

### Reviewer（代码审查）

- **会话名**：`<填写会话名，如 reviewer-main>`
- **职责**：
  - 独立读取代码和契约
  - 检查：正确性、边界、测试、风险
  - 判断问题严重程度，决定是直接要求修复还是升级
  - 通过后标记为"可合并"
- **判断边界**：
  - 轻微问题（测试不足、风格、边界值）：直接告诉 Worker 修复
  - 严重问题（架构冲突、安全风险、连续三次失败）：升级给 Architect
- **不做**：自己修改代码、替 Worker 做决策、绕过 Architect 改架构

### 升级路径

```text
Worker → Reviewer → Architect → 人
```

### 人的介入时机

**Architect 必须唤醒人**：
- 技术方案有多个选择，各有利弊
- 架构约束冲突
- 需要改变项目范围或优先级
- 预算、时间、风险判断

**Reviewer 必须唤醒人**：
- 安全或数据泄露风险
- Worker 连续 3 次未能通过审查
- 发现 Architect 的架构决策有根本问题

**Worker 基本不唤醒人**（通过 Reviewer 或 Architect 间接反馈）

### 接口约定

**任务包格式**（Architect → Worker）见 docs/HANDOFF.md 或任务 issue，必须包含：
- 范围（文件、接口、依赖）
- 契约（输入、输出、错误处理、性能）
- 验收标准（测试覆盖、安全检查）
- 不在范围内（明确排除的功能）

**审查报告格式**（Reviewer → Worker/Architect）必须包含：
- 结论（✅ 通过 / ❌ 需要修复 / ⚠️ 需要升级）
- 必须修复（问题、位置、原因）
- 建议改进（非阻塞）
- 需要 Architect 裁定（架构问题）

**状态交接格式**（Architect 维护 docs/HANDOFF.md）必须包含：
- 当前状态（各模块进展）
- 下一步（任务分配）
- 阻塞（等待什么）
- 当前架构约束

## 设计原理（实例化时删除以下内容）

### 核心矛盾

**Agent 协作的核心矛盾**：
1. **上下文是稀缺资源** — 每个 Agent 的记忆有限，堆细节会挤掉全局理解
2. **决策需要全局视野** — 架构、取舍、优先级必须基于完整项目理解
3. **执行需要局部聚焦** — 写代码时需要大量当前模块的细节

### 分工原则

**推导出的分工原则**：
- **决策者保持轻量上下文**：只记录决策依据、架构边界、当前状态
- **执行者获得局部全貌**：完整理解当前子任务，但不需要知道其他模块
- **验证者独立重建判断**：从代码本身和契约出发，不依赖执行者的解释

### Architect 如何保持轻量

**只记录决策，不记录实现**：

```markdown
# docs/HANDOFF.md（Architect 维护）
## 当前状态
模块 A：接口已定义，等待实现
模块 B：实现完成，已通过审查，待合并
模块 C：发现性能问题，需要重新设计缓存策略

## 下一步
- Worker-1: 实现模块 A 的用户认证
- Worker-2: 修复模块 C 的缓存策略
- Reviewer: 审查模块 A
```

**Architect 不看具体代码**：
- Worker 完成后，Architect 只看 Reviewer 的审查摘要
- 只有 Reviewer 升级的架构问题才需要 Architect 介入
- 合并时 Architect 看 git log，不看 diff

### 任务包示例

```markdown
# Task: 实现用户认证模块

## 范围
文件：`src/auth/`
接口：见 `docs/api/auth.md`
依赖：`src/db/user-repo.ts`（只读）

## 契约
- 输入：username + password
- 输出：JWT token or error
- 错误处理：3次失败锁定账户
- 性能：登录 < 500ms（P95）

## 验收标准
- [ ] 单元测试覆盖：正常、密码错误、账户不存在、锁定
- [ ] 集成测试：真实数据库
- [ ] 安全检查：密码不落日志，token 不泄露

## 不在范围内
- 注册功能（另一个任务）
- OAuth（V2）
```

### 审查报告示例

```markdown
# Review: 用户认证模块

## 结论
❌ 需要修复（Minor）

## 必须修复
1. 密码错误日志中包含了用户输入，违反安全约束
   位置：`src/auth/login.ts:45`

2. 缺少账户锁定的测试
   任务包要求覆盖，但只有 TODO

## 建议改进（非阻塞）
- 考虑用常量提取重试次数（当前硬编码为 3）

## 需要 Architect 裁定
无
```

### 常见问题

**Q: Architect 如何避免被细节淹没？**

A: **纪律：永远不看具体代码**。只看：
- Reviewer 的审查摘要
- Git log 的提交信息
- docs/HANDOFF.md 的状态更新

需要细节时，问 Reviewer 或 Worker，让他们提炼摘要。

**Q: Worker 如何知道任务边界？**

A: **任务包必须明确"不在范围内"**。不清楚时停下来问 Architect，不要猜。

**Q: Reviewer 的审查标准从哪里来？**

A: 三个来源：
1. 任务包中的契约和验收标准
2. 项目 docs/STANDARDS.md
3. Reviewer 自己的代码质量判断

**Q: 多个 Worker 如何协调？**

A: **通过 Architect 协调，Worker 之间不直接对话**。需要协调时：
- Worker 发现依赖问题 → 报告给 Reviewer → 升级给 Architect
- Architect 调整任务包或模块边界

**Q: 什么时候可以简化为双 Agent？**

A: 当：
- 人可以快速做代码审查（项目不复杂）
- 只有一个模块在开发（不需要并行）
- 迭代周期短（< 2 周）

简化为：Architect（决策）+ Worker（实现），人做审查。

**Q: 什么时候只需要单 Agent？**

A: 当：
- 任务很小（< 5 个文件）
- 没有架构决策（纯实现）
- 人可以直接给出详细需求

单 Agent 既做决策也做实现，人做最终验收。

### 项目文档组织

采用多 Agent 协作的项目需要实例化以下文档：

```text
目标项目/
├── AGENTS.md              ← 项目入口，声明采用多 Agent 协作
└── docs/
    ├── ROLES.md           ← 从本模板实例化，定义具体角色和会话名
    ├── HANDOFF.md         ← Architect 维护，当前状态和任务分配
    ├── STANDARDS.md       ← 从 agentic-work-infra 复制的执行约束
    ├── LESSONS.md         ← 失败经验，审议后晋升到规则（按需）
    ├── ARCHITECTURE.md    ← 架构文档，单文件（按需）
    └── architecture/      ← 架构文档，目录管理（大项目按需）
```

**AGENTS.md** 声明协作模式：
```markdown
## 协作模式
本项目采用多 Agent 协作模式，角色定义见 [docs/ROLES.md](docs/ROLES.md)

## 优先读取
1. [角色定义](docs/ROLES.md)
2. [通用工作标准](docs/STANDARDS.md)
3. [当前状态](docs/HANDOFF.md)
```
