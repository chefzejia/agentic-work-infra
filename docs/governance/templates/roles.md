## 模板部分（供项目实例化）

本项目启用三角色协作。当前活跃角色：

### Brain（协调者 + 架构师）

- **会话名**：`<填写会话名，如 brain>`
- **职责**：
  - 理解业务目标、做架构决策
  - 制定模块边界、接口契约、交接计划
  - 维护 docs/HANDOFF.md（当前状态、下一步、阻塞）
  - 制定任务包，分发给 Worker
  - 制定验收标准，交给 Tester
  - 协调 Worker 和 Tester 的工作流
  - 处理 Tester 升级的架构问题
- **只保留上下文**：目标、边界、当前状态、关键决策
- **不做**：写具体实现代码、执行测试

### Worker（实现者）

- **会话名**：`<填写会话名，如 worker-模块名>`
  - 示例：worker-auth、worker-payment、worker-api
- **职责**：
  - 读取任务包：范围、契约、验收标准
  - 实现功能代码
  - 写单元测试、自验证
  - 提交代码给 Tester
  - 根据 Tester 反馈修复问题
- **只关注**：当前任务的范围和契约
- **不做**：跨模块决策、架构调整、做验收判断

### Tester（验收者）

- **会话名**：`<填写会话名，如 tester>`
- **职责**：
  - 独立读取代码、任务包、验收标准
  - 阶段 1：静态审查（代码审查）
  - 阶段 2：动态验证（集成测试 + 部署验证）
  - 判断问题严重程度，决定是直接要求修复还是升级
  - 输出验收报告
- **判断边界**：
  - ✅ 通过：通知 Brain "可上线"
  - ❌ 实现问题：告诉 Brain 哪里需要修复，Brain 重新启动 Worker
  - ⚠️ 契约问题：升级给 Brain（契约定义错了或冲突了）
- **不做**：自己修改代码、替 Worker 做决策、绕过 Brain 改架构

### 升级路径

```text
Worker → Tester → Brain → 人
```

### 人的介入时机

**Brain 必须唤醒人**：
- 技术方案有多个选择，各有利弊
- 架构约束冲突
- 需要改变项目范围或优先级
- 预算、时间、风险判断

**Tester 必须唤醒人**：
- 安全或数据泄露风险
- Worker 连续 3 次未能通过验收
- 发现 Brain 的架构决策有根本问题

**Worker 基本不唤醒人**（通过 Tester 或 Brain 间接反馈）

### 接口约定

**任务包格式**（Brain → Worker）见 docs/HANDOFF.md 或任务 issue，必须包含：
- 范围（文件、接口、依赖）
- 契约（输入、输出、错误处理、性能）
- 验收标准（测试覆盖、安全检查）
- 不在范围内（明确排除的功能）

**验收报告格式**（Tester → Brain）必须包含：
- 结论（✅ 通过 / ❌ 实现问题 / ⚠️ 契约问题）
- 静态审查结果
- 动态验证结果
- 必须修复（问题、位置、原因）
- 需要 Brain 裁定（架构问题）

**状态交接格式**（Brain 维护 docs/HANDOFF.md）必须包含：
- 当前状态（各模块进展）
- 下一步（任务分配）
- 阻塞（等待什么）
- 当前架构约束

## 设计原理（实例化时删除以下内容）

### 第一性原理

**角色边界成立的唯一依据**：合并它会产生一个可以说出名字的具体失败。

**模型强度的边界**：
- 能力差异不是拆分理由（同一强模型既能规划又能写码又能审查）
- 信息差异才是拆分理由（Worker 的"我为什么这么写"让他看不见"这么写对不对"）

### 为什么是三个角色

**Brain = Architect**（必须合并）：
- 两者需要同一份上下文（项目目标、边界、当前状态、架构决策）
- 两者产出同一类产物（决策和任务分配）
- 在项目唯一的场景下，项目级上下文 = 架构上下文
- 拆分只会增加一次"互相转述"的成本，没有任何隔离收益

**Tester = Reviewer**（必须合并）：
- 两者需要同一份上下文（契约 + 代码）
- 两者产出同一个产物（通过/不通过的结论）
- 代码审查和测试执行是同一个验收流程的两个**阶段**，不是两个角色
- 拆分会导致 Reviewer 的"代码有问题"和 Tester 的"跑不通"需要协调，增加成本

**Worker ≠ Tester**（唯一必须保留的边界）：
- **作者给自己发合格证** — 验证退化成自我确认
- Worker 的上下文包含"我为什么这么写"，这个信息本身让他看不见"这么写对不对"
- 这是信息差异，不是能力差异，模型再强也解决不了

### Brain 如何保持轻量

**只记录决策，不记录实现**：

```markdown
# docs/HANDOFF.md（Brain 维护）
## 当前状态
模块 A：接口已定义，等待实现
模块 B：实现完成，已通过验收，待合并
模块 C：发现性能问题，需要重新设计缓存策略

## 下一步
- Worker-1: 实现模块 A 的用户认证
- Worker-2: 修复模块 C 的缓存策略
- Tester: 验收模块 A
```

**Brain 不看具体代码**：
- Worker 完成后，Brain 只看 Tester 的验收摘要
- 只有 Tester 升级的架构问题才需要 Brain 介入
- 合并时 Brain 看 git log，不看 diff

### 适配"直接上线部署调试"

**Tester 的动态验证阶段**：
1. 静态审查通过后，直接部署到生产
2. 执行关键路径验证（登录、支付等核心功能）
3. 监控错误日志（5-10 分钟）
4. 如果生产验证通过 → 报告"✅ 通过"
5. 如果生产出现问题 → 报告"❌ 实现问题"或"⚠️ 契约问题"

**风险控制**：
- Tester 必须先通过静态审查（不能盲目部署）
- 部署后立即验证关键路径
- 有错误立即回滚或标记为"实现问题"

### 任务包示例

```markdown
# Task: 实现用户认证模块

## 范围
文件：`src/auth/`
接口：见 `docs/api/auth.md`
依赖：`src/db/user-repo.ts`（只读）

## 契约
- 输入：username + password
- 输出：JWT token or error
- 错误处理：3次失败锁定账户
- 性能：登录 < 500ms（P95）

## 实现要求
- 写单元测试（正常、密码错误、账户不存在、锁定）
- 单元测试全部通过后提交

## 验收标准（Tester 执行）
- [ ] 代码符合契约
- [ ] 安全检查：密码不落日志
- [ ] 集成测试：与数据库交互正常
- [ ] 部署测试：生产环境能成功登录

## 不在范围内
- 注册功能（另一个任务）
- OAuth（V2）
```

### 验收报告示例

```markdown
# 验收报告：用户认证模块

## 结论
❌ 实现问题（需要修复）

## 静态审查
✅ 逻辑正确
✅ 边界清晰
❌ 安全问题：密码错误日志中包含了用户输入（src/auth/login.ts:45）

## 动态验证
⚠️ 未执行（等待修复后再测）

## 必须修复
1. 移除日志中的用户输入，只记录"密码错误"
   位置：src/auth/login.ts:45

## 升级给 Brain
无
```

### 常见问题

**Q: Brain 如何避免被细节淹没？**

A: **纪律：永远不看具体代码**。只看：
- Tester 的验收摘要
- Git log 的提交信息
- docs/HANDOFF.md 的状态更新

需要细节时，问 Tester 或 Worker，让他们提炼摘要。

**Q: Worker 如何知道任务边界？**

A: **任务包必须明确"不在范围内"**。不清楚时停下来问 Brain，不要猜。

**Q: Tester 的验收标准从哪里来？**

A: 三个来源：
1. 任务包中的契约和验收标准
2. 项目 docs/STANDARDS.md
3. Tester 自己的代码质量和风险判断

**Q: 单元测试 vs 验收测试？**

A:
- **单元测试**：Worker 写，Worker 自己跑，目的是快速反馈，不是合格证
- **验收测试**：Tester 执行（集成测试 + 部署验证），目的是判断"能不能上线"，是合格证

**Q: 多个 Worker 如何协调？**

A: **通过 Brain 协调，Worker 之间不直接对话**。需要协调时：
- Worker 发现依赖问题 → 报告给 Tester → 升级给 Brain
- Brain 调整任务包或模块边界

### 项目文档组织

三角色协作项目需要实例化以下文档：

```text
目标项目/
├── AGENTS.md              ← 项目入口，声明采用三角色协作
└── docs/
    ├── ROLES.md           ← 从本模板实例化，定义具体角色和会话名
    ├── HANDOFF.md         ← Brain 维护，当前状态和任务分配
    ├── STANDARDS.md       ← 从 agentic-work-infra 复制的执行约束
    ├── LESSONS.md         ← 失败经验，审议后晋升到规则（按需）
    ├── ARCHITECTURE.md    ← 架构文档，单文件（按需）
    └── architecture/      ← 架构文档，目录管理（大项目按需）
```

**AGENTS.md** 声明协作模式：
```markdown
## 协作模式
本项目采用三角色协作模式，角色定义见 [docs/ROLES.md](docs/ROLES.md)

## 优先读取
1. [角色定义](docs/ROLES.md)
2. [通用工作标准](docs/STANDARDS.md)
3. [当前状态](docs/HANDOFF.md)
```
