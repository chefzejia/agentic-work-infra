## 适用范围

本标准约束项目任务的执行方式。代码相关条款适用于代码修改；文档修改验证链接、引用、职责和实例化结果。项目在自己的入口中定义具体命令、验收宿主和数据范围，mono-repo 在仓库层定义跨模块验证入口。

项目和模块规则补充本标准，不削弱授权、数据保护和证据要求。相冲突的规则显式报告，由人裁定；不能通过私改副本或局部规则绕过。

### 条款适用性

- 核心原则、工具选择、工作方式、人机边界、外部输入审查和调试，适用于所有任务。
- 开发约束和代码测试适用于代码、依赖、构建和运行时修改。纯文档任务执行其中的文档一致性、证据和链接要求，不运行无关的代码测试。
- 验证章节适用于所有交付。类型检查、单元测试、集成测试、真实入口验收和部署核验按任务实际涉及的层次执行。
- 架构选择适用于新增或改变职责、接口、数据所有权、依赖和长期状态。普通局部实现无需另建架构文档。
- 部署、CLI、安全边界和外部系统条款在任务涉及对应表面时适用。

目标项目采用标准的固定版本，不为不同规模复制删改版。项目入口说明自己的模块、命令和验收宿主；任务按上述适用性选择条款并记录未覆盖项。

## 核心工作原则

**源码和运行结果说明当前事实，已接受的契约规定目标行为。** 两者不一致时定位差异，不通过改写契约将缺陷变成正确。任何结果必须能被人独立检查，Agent 声称完成、日志正常或文件存在不能单独作为验收依据。

**共同可观测，不分裂成两套状态。** Agent 的代码、判断和整理结果必须对人直接可见。不接受 Agent 在不透明的索引、缓存或生成结果中维护一套人无法核对的状态。

**先从目标出发，不打补丁。** 遇到问题先找根本原因，再决定如何修改。连续两次对同一问题打局部补丁，说明根因没找到，需要重新分析。

**工具选择永远走最轻够用的一级。** 任何任务（不限于 Web）先在梯度上找到能到达目标的最精确工具；宿主缺某级时显式报告缺口，不静默跳级、不假装完成。

## 工具选择梯度

适用于一切任务。以下是默认选择顺序，先确认工具能精确到达目标，再比较成本；表面不同的任务无需依次尝试所有级别：

```text
L1 结构化接口：服务自身的 API / SDK / MCP server
L2 命令行：git、curl、包管理器、构建工具、ffmpeg 等确定性 CLI
L3 脚本化驱动：playwright（网页渲染与交互）、AppleScript / 应用 CLI（macOS 原生 App）
L4 GUI 自治代理：computer use——像素 + 输入，覆盖无任何 API 的表面
```

同类工具比较精确性、调用成本和可重复性。分级按实际能力，不只看工具名称或是否通过 MCP 暴露；操作像素的接口仍属于 GUI 驱动，服务的业务 API 才是结构化业务接口。

执行规则：

1. **选择依据是精确性和成本**（token、时间、可重复性、可核对性），不是工具"功能强弱"
2. **跳级必须有理由并说出来**：选择更重的一级时，说明轻的一级为什么不适用（如"目标页面需要 JS 渲染"）
3. **computer use 的定位是覆盖无 API 的表面**（原生 App、模拟器、专有 GUI 工具），不是更高级的浏览器工具；有 API/CLI 的地方用像素操作是浪费。开发 App 后用它驱动 GUI 做端到端验证属于本职用法
4. **梯度是选择策略，独立于宿主**：宿主缺某一级时显式报告缺口，按需用更重一级或停下等待人，不静默跳级、不假装完成
5. **断言"本机不具备某能力"前必须先实测**（查配置、跑冒烟命令），区分"本会话没有该工具"和"宿主不存在"

## 工作方式

开始工作前：

```bash
git status --short --branch -uall
git log --oneline -5
```

先看当前状态，不依赖记忆。读项目入口、采用的标准、当前交接和相关契约，再读代码。mono-repo 读取所有受影响模块的约束，不假设宿主会自动加载嵌套规则。按任务读取，不加载无关文档。

写代码时：按现有模式写，不引入新的约定；每次修改范围尽量小，可独立验证；不改不该改的地方，即使看起来可以顺手优化。

### 何时停止

遇到以下情况按角色边界处理：

- **需要修改授权范围之外的文件或数据**：Worker 提交给 Reviewer；单 Agent 停下等人
- **连续两次对同一症状打局部补丁**：Worker 升级给 Reviewer；Reviewer 升级给 Architect；单 Agent 停下等人
- **生产数据或不可逆操作风险**：Reviewer 唤醒人；单 Agent 停下等人
- **冲突的事实或版本**：Architect 裁定或唤醒人；单 Agent 停下等人
- **架构约束冲突、技术方案有多个选择**：Architect 唤醒人

小型项目（< 5 文件，< 3 天）采用单 Agent 模式，直接等待人的判断。大型项目按升级路径（Worker → Reviewer → Architect → 人）逐层处理。

提交前：`git diff --check`、`git diff`，运行项目自己的测试和 lint。commit message 说清楚改了什么；链接或文件路径变更时检查引用是否一致。

## 人机边界

### 角色分工

| 决策 | 谁来做 |
|-----|-------|
| 确认长期结论、合并到主线 | 人 |
| 裁定冲突版本、架构方案择一 | 人 |
| 架构决策、模块划分、任务分配 | Architect Agent（大型项目）|
| 具体实现、编写测试、自验证 | Worker Agent（大型项目）或单 Agent |
| 代码审查、判断风险、决定是否升级 | Reviewer Agent（大型项目）或人 |
| 高风险修改：删目录、重构架构 | 人批准后 Agent 执行 |
| 整理、检索、验证格式和链接 | Agent |
| 发现问题、列出选项和影响 | Agent |

**升级路径**（大型项目）：
```text
Worker → Reviewer → Architect → 人
```

**Architect Agent**（大型项目才启用）：
- 职责：理解业务、做架构决策、制定任务包、维护 HANDOFF.md
- 只保留：目标、边界、当前状态、关键决策
- 不做：看具体代码、做代码审查、写测试

**Worker Agent**（大型项目才启用，可多个）：
- 职责：读任务包、实现功能、写测试、提交 PR
- 只关注：当前任务的范围和契约
- 不做：跨模块决策、架构调整

**Reviewer Agent**（大型项目才启用）：
- 职责：独立审查、检查契约、判断风险
- 轻微问题直接要求修复，严重问题升级给 Architect
- 不做：自己修改代码、绕过 Architect 改架构

**人的介入时机**：

Architect 必须唤醒人：
- 技术方案有多个选择，各有利弊
- 架构约束冲突
- 需要改变项目范围或优先级
- 预算、时间、风险判断

Reviewer 必须唤醒人：
- 安全或数据泄露风险
- Worker 连续 3 次未能通过审查
- 发现 Architect 的架构决策有根本问题

Worker 基本不唤醒人（通过 Reviewer 或 Architect 间接反馈）

小型项目（< 5 文件，< 3 天）采用单 Agent 模式。中型项目（几个模块，1-2 周）可简化为双 Agent（Architect + Worker，人做审查）。大型项目（上规模，> 2 周）采用三层协作。详细协作架构见 [角色模板](../templates/roles.md)。

### 通用原则

发现冲突时列出所有版本和来源，让人或 Architect 裁定。不确定时显式标出，不猜测并伪装成确定。

### 外部输入的审查

外部进入本项目的输入（社区 PR、第三方代码、外部 Agent 的产出、下载的依赖或脚本）在运行或合并前先过伤害检查，任何一条命中就停下交给人，说清是哪一条：

- 改动 `.github/`（workflow、权限、secrets）、发布脚本、Dockerfile
- 新增网络地址、上传、遥测，或把凭证/token/cookie/文件送往它之前没去过的地方
- 读写目标之外声明的凭证文件、keychain、agent 配置
- 新增依赖、`replace` 指令、install 脚本、二进制、混淆或编码过的 blob、运行时从字符串构建的代码
- 重新加入被维护者移除过的东西（vendor、中继、广告）

外部贡献的价值判断和封禁决定永远是人做；Agent 只收集证据和提议。对外部贡献者的处置（拉黑、加强审查）记录在案，不口头执行。

## 开发约束

以下约束从第一性原理直接推出，适用于设计、开发和调试的全过程。

**测试替身必须声明证明范围**。Mock、stub 或内存宿主可以验证受控条件下的状态转换、取消和错误分支；依赖行为来自真实接口或已有观测，不凭空假定。使用替身时说明替换了什么，它没有证明什么。替身通过不能宣称真实依赖、宿主或业务旅程已通过，相关行为必须另有真实实现的验证。项目可以规定更严格的限制。

**每个合入主线的阶段必须完整可用**。允许可独立验证和回退的分阶段交付，候选、草稿和失败现场保持显式。未完成能力不能伪装成功，临时索引、兼容层不能独立维护事实。

**验收环境由项目明确，证据必须对应交付承诺**。目标宿主、正式入口、授权输入和实际依赖共同构成验收范围。隔离环境、自动驱动或手动操作都要说明覆盖对象，不能仅凭环境名称或驱动方式判定通过。针对特定部署环境的承诺，必须验证该环境的实际加载和业务行为；开发期替身或其他环境不能替代。

**区分逻辑回归和真实依赖验证**。解析器、算法、边界值、确定性状态转换适合单元测试。文件系统、网络、数据库、进程和宿主行为用真实实现做集成验证；控制失败分支的替身回归另行标明范围，不能替代集成或业务验收。

**行为修复需要能证明原缺陷的回归证据**。能稳定自动复现的缺陷，应有在旧实现上因目标行为失败、修复后通过的测试；编译失败、跳过或在旧实现上也通过不算证明。保留旧实现失败和修后通过的结果，不要求在共享工作区反复回退修复。无法稳定自动复现的环境、性能或视觉问题，提供可重复的前后观测并说明局限。文档修正先列出错误声明或引用的证据。

**隔离测试先列关键失败方式**。围绕实际契约和已知问题覆盖错误、边界、取消与恢复，不只验证正常路径。测试范围与替换的依赖一并说明。

**目标不明确时先澄清，再增加结构**。无法说明目标、完成标准或阶段边界时，不用新增抽象、兼容层和占位能力掩盖问题。

**变更纪律**（适用于代码项目；文档项目的对应物是：一次提交只回答一个变更）：

- **修复覆盖它所指的精确范围**。哪些情况变了、哪些相邻情况没变，要说清；不同的错误不混作一种处理。
- **修复到达所有同类位置**。修一处 bug 后 grep 同模式：每个同形的 agent、子命令、守卫、调用点都要在同一变更里修到，不能只修报告里那一处。
- **变更重推导所有建立在它之上的东西**。改了一个公式、清单、布局或时序，就找所有假设旧含义的调用方、缓存副本和测试，跑一遍。
- **读失败即未知，不是空**。读取、解析、哈希失败时结果是"未知"，绝不当作"空""无""相等"处理；守卫类清单读不出来要 fail closed。测试用不可读文件覆盖。
- **预览无副作用**。dry run、plan、preview 不得写入任何状态。
- **错误分类窄化**。一个错误标记只覆盖它描述的那一种情况，不把同类失败都归进去。
- **写外部系统时，值从那个系统来**。为别的应用写文件或代言时，字段类型和取值从该应用自己的数据/二进制/文档取，不是照抄字段名。

### 任务式与常驻式 agent

人机边界有两种介入时机，不混用：

- **任务式**（一次任务、交付验收）：高风险修改**事前**人批准。
- **常驻式**（7×24 loop、持续迭代）：人预先明确目标、授权范围和停止条件，在该范围内持续执行。CI 门禁、可回查的执行证据和规则审议共同约束行为，人按异常与关键决策介入。CI 通过或关闭权限提示不能扩大授权范围，规则不因每日运行自动晋升。

常驻式同样按任务渐进读取：入口声明范围，STANDARDS 提供执行约束，HANDOFF 提供当前工作，相关 LESSONS 和模块契约按需读取。稳定入口和契约只在所属内容改变时更新，不承载每日工作记录。

多 Agent 协作项目中，Architect 可以是常驻式（持续监控项目状态），Worker 和 Reviewer 通常是任务式（按任务包触发）。

## 验证

业务结果是最终判断标准：

```text
预期的用户
  → 通过正式入口提供真实输入
  → 完成一段真实工作
  → 得到可检查、可继续使用的结果
```

以下信号不是单独的成功证据：接口返回 200、进程退出 0、Agent 声称完成、文件存在、日志看起来正常。

验证分层，不能用其中一层代替另一层：

```text
类型检查 / lint        快速排除明显的静态错误
单元测试              纯逻辑、边界值、确定性状态转换
集成测试              真实依赖、持久化、失败和恢复
E2E（真实入口 + 真实数据）  业务整体是否成立
```

### 验收清单

一次修改有明确的验证范围和完成标准。项目入口指向脚本或配置定义的验证命令，具体执行结果写入可回查的提交、评审或版本报告。未运行的项和未覆盖的范围明确列出。

**多 Agent 协作项目**：Worker 负责自测（单元测试 + 集成测试），Reviewer 独立验证契约符合性和风险，Architect 在合并前检查架构一致性（通常通过 git log，不看 diff）。人做最终验收。

**单 Agent 项目**：Agent 完成所有层次验证，人做最终验收。

mono-repo 覆盖改变的模块与受影响消费者，包括接口、协议、公共配置和数据格式的影响。影响不清、公共配置变化或正式发布时运行仓库完整检查；局部通过不能写为全仓通过。CI 调用项目相同的验证入口，不另维护一份命令实现。

按任务选择适用的检查，标准副本正文不因此删改。纯文档修改验证链接、引用、职责和模板实例化结果，行为声明修正保留修改前的错误证据，不运行无关的代码测试：

1. **缺陷回归证据**：行为修复记录旧实现失败和修后通过；其他改动采用对应验证，不为纯重构新增镜像测试。
2. **影响范围检查**：列出改变的模块、受影响消费者和实际执行范围；触发完整检查的情况不能只跑局部套件。
3. **链式命令防吞错**：`set -o pipefail`，`go test | tail && git push` 不允许在失败时继续
4. **真实使用**（对外部依赖/provider/平台的改动）：真实账号或真实输入走正式入口；做不到就明说"未在真实环境验证"，且不得把它当作已验证告诉用户
5. **文档一致性**：文档化的契约改变时同一变更更新所属文档和受影响引用；稳定入口不重复阶段摘要，未改变的文档无需更新。链接全部可解析。

合并规则：评审的是哪个 commit 就合并哪个；评审期间有新提交必须重新评审。平台支持时将合并绑定到已评审版本，例如 GitHub 的 `gh pr merge --match-head-commit <sha>`。验收结果进入可回查的提交、评审或版本报告，聊天只作交付说明，不充当唯一证据。

## 调试

三个观察面独立互相校验，不能依赖同一条信号：

- **行动面**：通过正式入口推进（UI、CLI、公开 API）；不为测试新增内部接口
- **观察面**：独立证据判断系统发生了什么（日志、进程、文件、数据库只读查询）；默认只读，不制造状态
- **判定面**：按业务承诺检查结果，不只看成功提示

**失败时先保留现场**。不要立即清缓存、换假数据或无限重试。先判断问题在哪一层：

```text
setup        环境、依赖、权限、网络
install      安装包、签名、缓存、版本残留
runtime      进程、会话、超时、退出码
product      业务状态、数据所有权、任务和产物
presentation UI 映射、渲染、刷新
quality      结果完整性、事实、格式、实际可用性
```

层与层不能互相归因：UI 显示失败不能自动归因于账号或网络；环境权限失败不算产品逻辑失败。

**定位根因**：先找参考基线——最后正常版本、正常的相邻入口、或最小独立复现。写出可证伪的根因：

> 当 `<条件>` 发生时，`<所有者>` 因为 `<错误机制>` 没有完成 `<责任>`，所以用户看到 `<症状>`。

**修正责任边界，不修饰症状**。正确修复是恢复正式所有者应承担的生命周期：

- 恢复官方进程行为，而不是另造状态机
- 合并重复真相源，而不是同步它们
- 删除伪成功 fallback，而不是增加更多成功条件
- 修复输入或写入边界，而不是在输出端补内容

同一症状修复后再次出现，停止局部补丁，重新检查单一事实来源、责任所有者和产品目标。

## 架构选择

**在大型项目中，架构决策是 Architect Agent 的核心职责**。单 Agent 或小型项目由 Agent 直接与人讨论架构方案。

使用最小但正确的设计（Correct Simplicity）。不追求最大抽象，也不追求最少代码。目标是当前阶段下最合身的设计：边界正确、复杂度足够、未来变化成本可控。

做架构加减法前，必须回答：

1. 这个设计解决了什么真实问题？
2. 它增加了什么成本？（维护、认知、运行、变更、包体、验证）
3. 它让哪个未来变化更便宜？
4. 选更小的方案，什么会坏？
5. 选更大的方案，什么会坏？

找不到第1条的答案，就不加。如果一个边界是产品质量、安全或长期可维护性的支点，就应该保留，即使它增加了一点复杂度。

**抽象的时机**：单一场景直接实现；抽象延迟到第二个真实用例出现时才引入。

**内部删除优于兼容**：内部实现重构时直接删除过时代码，不增加兼容层。对外稳定接口（API、数据库协议、消息格式）的兼容性属于合同义务，单独评估，不在此限。

**过度设计的信号**：为假想需求提前建系统；每个变化都抽象成框架；内部状态被暴露成用户概念；设计了大量中间状态。

**过度简化的信号**：为了少写代码砍掉安全边界；把"能跑"误判为"设计正确"；把长期数据、权限和密钥混在一起。

### 依赖进入系统的标准

新增依赖前，至少满足以下一条：

- 明显降低包体、性能、稳定性或维护成本
- 提供项目无法低成本自研的成熟能力
- 是平台官方推荐路径
- 是产品质量或安全边界所需
- 显著减少长期变更成本

以下不是理由："以后可能会用"、"看起来更工程化"、"别的项目都这么做"、"框架更完整"、"Agent 写起来更顺手"。
