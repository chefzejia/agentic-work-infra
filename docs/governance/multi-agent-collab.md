# 多 Agent 协作架构

## 适用场景

项目规模和复杂度决定协作模式：

| 项目规模 | 协作模式 | 说明 |
|---------|---------|------|
| 小型（< 5 文件，< 3 天） | 单 Agent | 你与一个 Agent 对话，它既做决策也做实现 |
| 中型（几个模块，1-2 周） | 双 Agent | Architect（决策）+ Worker（实现），你做审查 |
| 大型（上规模，> 2 周） | 多 Agent | Architect + Worker(s) + Reviewer，你做裁决 |

本文档定义大型项目的多 Agent 协作架构。中小型项目可以简化或不使用。

## 核心矛盾与设计原则

**Agent 协作的核心矛盾**：
1. **上下文是稀缺资源** — 每个 Agent 的记忆有限，堆细节会挤掉全局理解
2. **决策需要全局视野** — 架构、取舍、优先级必须基于完整项目理解
3. **执行需要局部聚焦** — 写代码时需要大量当前模块的细节

**推导出的分工原则**：
- **决策者保持轻量上下文**：只记录决策依据、架构边界、当前状态
- **执行者获得局部全貌**：完整理解当前子任务，但不需要知道其他模块
- **验证者独立重建判断**：从代码本身和契约出发，不依赖执行者的解释

## 三层协作架构

```text
┌─────────────────────────────────────────┐
│  Architect Agent（架构师）               │
│  - 理解业务目标、做架构决策              │
│  - 制定模块边界、接口契约、交接计划      │
│  - 只保留：目标、边界、当前状态、阻塞    │
│  - 不接触具体实现细节                    │
└─────────────────┬───────────────────────┘
                  │ 发布任务包
                  ↓
┌─────────────────────────────────────────┐
│  Worker Agent（执行者，可以多个）        │
│  - 读取任务包：范围、契约、验收标准      │
│  - 实现功能、写测试、自验证              │
│  - 完成后提交给 Reviewer                 │
│  - 不需要知道其他模块的实现              │
└─────────────────┬───────────────────────┘
                  │ 提交 PR
                  ↓
┌─────────────────────────────────────────┐
│  Reviewer Agent（代码审查者）            │
│  - 独立读取代码和契约                    │
│  - 检查：正确性、边界、测试、风险        │
│  - 轻微问题：直接告诉 Worker 修复        │
│  - 严重问题：升级给 Architect 重新决策   │
│  - 通过后：标记为"可合并"                │
└─────────────────┬───────────────────────┘
                  │ 
                  ↓
┌─────────────────────────────────────────┐
│  人（项目负责人）                        │
│  - 在 Architect 层：确认目标、裁定架构   │
│  - 在 Reviewer 层：抽查或批准高风险      │
│  - 在 Worker 层：基本不介入               │
└─────────────────────────────────────────┘
```

## 角色定义

### Architect Agent（架构师）

**职责**：
- 与人沟通，理解业务目标和约束
- 做架构决策：模块划分、接口设计、技术选型
- 维护 HANDOFF.md：当前状态、下一步、阻塞
- 制定任务包，分发给 Worker
- 处理 Reviewer 升级的架构问题

**只保留的上下文**：
- 业务目标和核心约束
- 架构边界和模块依赖
- 当前状态：哪些模块完成、哪些在进行、哪些阻塞
- 关键决策记录和理由

**不做的事**：
- 不看具体代码实现
- 不做代码审查
- 不写测试用例
- 不关注实现细节

**Architect 保持轻量的方式**：
- Worker 完成后，只看 Reviewer 的审查摘要，不看 diff
- 只有 Reviewer 升级的架构问题才需要介入
- 合并时看 git log 摘要，不看具体改动

### Worker Agent（执行者）

**职责**：
- 读取 Architect 给出的任务包
- 实现功能、写测试、自验证
- 提交 PR 给 Reviewer
- 根据 Reviewer 反馈修复问题

**获得的上下文**：
- 任务包：范围、契约、验收标准、不在范围内
- 当前模块的完整代码
- 依赖模块的接口定义（不需要实现细节）
- 项目 STANDARDS.md

**不做的事**：
- 不做跨模块决策
- 不修改架构边界
- 不查看其他模块的实现（除非任务包明确要求）

**工作流程**：
1. 读任务包 + 项目 STANDARDS.md
2. 实现 + 自测
3. 提交 PR，附上自查清单
4. 等 Reviewer 反馈
5. 修复问题或升级给 Architect

### Reviewer Agent（代码审查者）

**职责**：
- 独立读取代码和契约
- 检查：正确性、边界、测试、风险
- 判断问题严重程度，决定是直接要求修复还是升级
- 通过后标记为"可合并"

**获得的上下文**：
- PR 的代码改动
- 任务包中的契约和验收标准
- 项目 STANDARDS.md
- 相关模块的接口定义

**不做的事**：
- 不自己修改代码
- 不替 Worker 做决策
- 不绕过 Architect 直接改架构

**判断边界**：

**直接要求 Worker 修复**（不升级）：
- 测试不足
- 代码风格不一致
- 边界值处理缺失
- 日志或错误信息不清楚
- 性能明显不达标
- 安全问题有明确修复方式

**升级给 Architect 重新决策**：
- 任务范围定义不清
- 接口设计不合理
- 需要修改其他模块
- 架构约束无法满足
- 安全风险需要架构层面解决
- Worker 连续三次未能通过审查

## 接口约定

### 任务包格式（Architect → Worker）

```markdown
# Task: <任务名称>

## 范围
文件：`<路径>`
接口：见 `<文档>`
依赖：`<模块>`（只读/可修改）

## 契约
- 输入：<参数和约束>
- 输出：<返回值和格式>
- 错误处理：<哪些情况、如何处理>
- 性能：<指标>

## 验收标准
- [ ] 单元测试覆盖：<哪些场景>
- [ ] 集成测试：<真实依赖>
- [ ] 安全检查：<具体要求>

## 不在范围内
- <明确排除的功能>
- <后续任务>
```

### 审查报告格式（Reviewer → Worker/Architect）

```markdown
# Review: <任务名称>

## 结论
✅ 通过 / ❌ 需要修复（Minor/Major）/ ⚠️ 需要升级

## 必须修复
1. <问题描述>
   位置：`<文件:行号>`
   原因：<违反了什么约束>
   
2. ...

## 建议改进（非阻塞）
- <优化建议>

## 需要 Architect 裁定
- <架构问题描述>
- <为什么需要升级>
```

### 状态交接格式（Architect 维护 HANDOFF.md）

```markdown
# Handoff

更新时间：<日期>

## 当前状态
- 模块 A：接口已定义，等待实现
- 模块 B：实现完成，已通过审查，待合并
- 模块 C：发现性能问题，需要重新设计缓存策略

## 下一步
- Worker-1: 实现模块 A 的用户认证
- Worker-2: 修复模块 C 的缓存策略
- Reviewer: 审查模块 A

## 阻塞
- 模块 D 依赖外部 API，等待接口文档

## 当前架构约束
- 所有模块通过事件总线通信，不直接调用
- 数据库访问只能通过 Repository 层
- 外部 API 调用必须有超时和重试
```

## 升级路径

```text
Worker 遇到问题
  ↓
能自己解决？
  是 → 直接修复
  否 → 提交给 Reviewer
  
Reviewer 审查
  ↓
轻微问题？
  是 → 告诉 Worker 修复
  否 → 升级给 Architect
  
Architect 判断
  ↓
架构调整？
  是 → 重新设计，更新任务包
  否 → 与人讨论
  
人裁决
  ↓
做出最终决定
```

## 人的介入时机

### Architect 必须唤醒人

- 技术方案有多个选择，各有利弊
- Worker 或 Reviewer 提出了架构约束冲突
- 需要改变项目范围或优先级
- 预算、时间、风险判断

### Reviewer 必须唤醒人

- 安全或数据泄露风险
- Worker 连续 3 次未能通过审查
- 发现 Architect 的架构决策有根本问题

### Worker 基本不唤醒人

通过 Reviewer 或 Architect 间接反馈。

## 项目文档组织

采用多 Agent 协作的项目需要实例化以下文档：

```text
目标项目/
├── AGENTS.md              ← 项目入口，声明采用多 Agent 协作
├── ROLES.md               ← 定义具体角色和会话名
├── HANDOFF.md             ← Architect 维护，当前状态和任务分配
├── STANDARDS.md           ← 从 agentic-work-infra 复制的执行约束
├── LESSONS.md             ← 失败经验，审议后晋升到规则
└── docs/
    └── architecture/      ← 架构决策记录（按需）
```

**AGENTS.md** 声明协作模式：
```markdown
## 协作模式
本项目采用多 Agent 协作模式，角色定义见 [ROLES.md](ROLES.md)

## 优先读取
1. [角色定义](ROLES.md)
2. [通用工作标准](STANDARDS.md)
3. [当前状态](HANDOFF.md)
```

**ROLES.md** 从模板实例化，定义当前活跃的角色和会话名。

## 常见问题

### Q: Architect 如何避免被细节淹没？

A: **纪律：永远不看具体代码**。只看：
- Reviewer 的审查摘要
- Git log 的提交信息
- HANDOFF.md 的状态更新

需要细节时，问 Reviewer 或 Worker，让他们提炼摘要。

### Q: Worker 如何知道任务边界？

A: **任务包必须明确"不在范围内"**。不清楚时停下来问 Architect，不要猜。

### Q: Reviewer 的审查标准从哪里来？

A: 三个来源：
1. 任务包中的契约和验收标准
2. 项目 STANDARDS.md
3. Reviewer 自己的代码质量判断

### Q: 多个 Worker 如何协调？

A: **通过 Architect 协调，Worker 之间不直接对话**。需要协调时：
- Worker 发现依赖问题 → 报告给 Reviewer → 升级给 Architect
- Architect 调整任务包或模块边界

### Q: 什么时候可以简化为双 Agent？

A: 当：
- 人可以快速做代码审查（项目不复杂）
- 只有一个模块在开发（不需要并行）
- 迭代周期短（< 2 周）

简化为：Architect（决策）+ Worker（实现），人做审查。

### Q: 什么时候只需要单 Agent？

A: 当：
- 任务很小（< 5 个文件）
- 没有架构决策（纯实现）
- 人可以直接给出详细需求

单 Agent 既做决策也做实现，人做最终验收。
