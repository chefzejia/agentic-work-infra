# 三角色协作设计原理

## 第一性原理：什么时候才应该拆分角色？

**角色边界成立的唯一依据：合并它会产生一个可以说出名字的具体失败。**

在多 Agent 系统中，每增加一个角色就会增加一次“上下文转述损耗”和“协调开销”。
- **能力差异不是拆分理由**：同一个高水平模型既能做架构设计，也能写业务代码，还能做代码审查。
- **信息差异（Context Asymmetry）才是拆分理由**：当某一段上下文的存在本身会干扰另一项判断时，才必须进行物理会话隔离。

## 为什么不多不少正好是三个角色？

### 1. 为什么 `Brain = Architect`（必须合并）
- **上下文同构**：项目协调者（Coordinator）与架构师（Architect）需要完全相同的上下文——项目目标、模块边界、当前全局进展与关键技术决策。
- **产物同构**：两者的核心产出都是“定义模块契约”与“拆解分配任务”。
- **合并收益**：在单一项目内，项目级上下文就是架构上下文。拆成两个角色只会增加一次无意义的互相转述。

### 2. 为什么 `Tester = Reviewer`（必须合并）
- **上下文同构**：代码审查（Code Review）与测试验收（QA Testing）面对的是同一份输入——《任务包》契约 + Worker 提交的代码。
- **产物同构**：两者的最终产出都是同一个结论——“是否符合契约、能否放行上线”。
- **合并收益**：静态审查（看代码）与动态验证（跑测试/部署验证）是**同一个验收流程的两个先后阶段**，而非两个对立角色。合并后可一次性输出完整的《验收报告》，避免 Reviewer 与 Tester 结论打架。

### 3. 为什么 `Worker ≠ Tester`（唯一不可妥协的隔离边界）
- **具体失败名称：“作者给自己发合格证”**。
- **不可溶解的信息差异**：Worker 在写代码的过程中，上下文里积累了大量“我为什么妥协、我为什么这么实现”的思维惯性。这种惯性会让同一个会话在自检时自动脑补合理性，对边界遗漏和契约偏差视而不见。
- **隔离收益**：独立的 Tester 会话只看“契约要求什么”和“代码实际写成了什么”，没有任何实现包袱，从而保证验收的客观性。

## Brain 如何避免被细节淹没？

多 Agent 协作最容易崩溃的地方是 Brain 的上下文爆炸。保持 Brain 轻量的三条铁律：
1. **看摘要，不看代码**：Brain 只读取 Tester 输出的结构化《验收报告》和 `git log --oneline`，不直接阅读模块具体实现代码。
2. **契约驱动控制流**：当 Tester 报告“❌ 实现问题”时，Brain 直接将报告转发给 Worker 修复；只有当 Tester 报告“⚠️ 契约问题”或 Worker 连续 3 次修复失败时，Brain 才介入重写契约。
3. **状态原地覆盖**：`docs/HANDOFF.md` 只保留当前活跃模块的状态快照，已验收合入的任务立即移出。

## 为什么禁止“多子 Agent 同时写小功能”（Performative Parallelism）

很多支持子 Agent 的宿主（如 Codex、Claude Code）默认倾向于将一个小需求拆成 3~5 个子任务并发派发。这种“表演式并发”在工程实践中效率极低，原因在于四重隐性税：

1. **冷启动重复阅读税（N × Context Tax）**：主会话已经读懂了仓库契约与 Schema；一旦拆给 $N$ 个子 Agent，每个子 Agent 醒来都要重新 `glob / grep / read` 同一批基础文件，Token 消耗翻 $N$ 倍，端到端耗时取决于最慢的那个子 Agent。
2. **共享工作区踩踏（Workspace Contention）**：多个写操作子 Agent 在同一工作树并发改代码时，会互相覆盖公共入口（如 `schema.py`、`App.svelte`、`router.py`），且一个子 Agent 的半成品代码会导致另一个子 Agent 的 `pytest / typecheck` 报错，进而引发连环误修。
3. **语义撕裂与缝合税（Integration Tax）**：同一个业务切面被拆给互不通气的多个子 Agent 后，命名、错误处理和状态流转各自为政，主控收回后花在排查冲突和缝合上的时间远超自己直接写完。
4. **指令序列化开销**：写几百字 Prompt 交代上下文 + 等待子 Agent 总结汇报的时间，往往比主会话直接执行 3 次 `edit` 慢数倍。

因此，**写操作默认串行（单工作区 Write = `1`）**；只有当**写集合 100% 物理正交 + 共享契约已提前冻结 + 独立 Worktree 隔离**时，才允许按完整垂直模块并行派发 `2 ~ 3` 个 Worker。只读探索（Read / Audit）无状态冲突，可按正交维度并发 `2 ~ 4` 个。

## 为什么是“状态去 Session 化 + 算力热驻留”？（Attention Conservation）

AI 时代的算力近乎无限，而**人类的注意力带宽存在硬物理上限（同时追踪超过 3~5 个会话即会迅速衰减）**。

1. **为什么领域状态必须“去 Session 化（Sessionless）”**：
   - 如果一个项目的架构约定、待办任务和进展只存在于某个聊天窗口（Session）的历史记录里，一旦会话重置或换另一个 Agent 接手，状态即刻丢失，人类就不得不去充当多个窗口之间的状态同步器。
   - 因此，所有契约与状态必须落盘为工作区文件（`PRODUCT.md` / `ARCHITECTURE.md` / `HANDOFF.md` / Git Commit）。任何新会话只需读取磁盘文件即可 100% 恢复项目状态。
2. **为什么执行节点应当“热驻留（Warm Teammates）”**：
   - “状态不依赖 Session”不等于“每次派活都要销毁重建 Session”。每次新建空白会话都会导致大模型的 **KV Prompt Cache（前缀缓存）归零**，迫使 Worker 重新扫描目录、重读基础契约，白交冷启动税。
   - 在支持持久队友编排的宿主中，Brain 创建具名 Worker 与 Tester 后，在后续波次（Wave N+1）通过增量消息持续复用该队友，即可同时获得**落盘状态的确定性**与**高达 90%+ 的前缀缓存命中率**。

## 与底层编排工具解耦

本协作模型是**纯逻辑协议**，不绑定任何特定软件：
- 在支持原生子 Agent 编排的宿主中，Brain 是主会话，Worker 与 Tester 是按任务派生并隔离上下文的子会话；
- 在多工作树桌面工具（如 Orca）或终端复用器（如 Herdr / tmux）中，三个角色映射为独立的持久或临时会话进程；
- 具体工具的 CLI 语法、进程守护与模型参数配置属于**宿主环境配置**，不应写入项目级治理协议。
