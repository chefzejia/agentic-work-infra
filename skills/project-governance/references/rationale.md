# 项目治理设计原理

## 为什么拒绝“跨仓复制大段静态标准”

在 Agent 时代，治理文档面临两个物理约束：

1. **注意力稀释（Context Dilution）**：每次会话让 Agent 先读几百行的通用软件工程教导，会严重稀释当前项目核心红线与业务契约的权重。
2. **副本腐败（Copy Drift）**：把通用标准复制到十个业务仓库，就制造了十份需要同步的静态副本，违背“单一事实来源”的第一性原理。

因此：
- **通用工程素养与工作方法**（如如何调试、如何写测试、如何做多 Agent 协作）应当封装为独立的 **Skills**（如 `engineering-discipline`、`multi-agent-collab`），按任务性质由 Agent 动态加载。
- **项目仓库内的文档**只记录**属于这个项目自己的事实与边界**（定位、架构契约、验证命令、踩坑记录）。

## 稳定契约 vs 动态状态

项目文档按生命周期分为两类，绝不混写：

| 类型 | 包含文档 | 更新频率与方式 |
| --- | --- | --- |
| **稳定契约** | `README.md`, `AGENTS.md`, `PRODUCT.md`, `ARCHITECTURE.md`, `DEPLOYMENT.md` | 仅当对外承诺、模块边界、公共接口或部署流程改变时，随代码在**同一个 Commit** 中更新。 |
| **动态状态** | `HANDOFF.md`, `LESSONS.md` | 随工作推进更新。`HANDOFF.md` 原地替换过期状态，不充当完成日志；历史验收结果留在 Git Commit 或 PR 记录中。 |

## 为什么砍掉中间态（RFC / 多份领域碎文档 / 文字版 DESIGN.md）

传统大团队研发流程依赖长链条的文字缓冲物（`PRD → DOMAIN → RFC → Figma/DESIGN.md → 接口文档 → 代码`），因为在人类组织中跨部门沟通昂贵、改代码慢。

但在 **高杠杆个体/小团队 + Agent 协同（AI-Native）** 模式下，写代码和改原型的速度已经远快于维护多份中间文档。保留长链条会带来严重的**上下文跳转损耗**与**契约撕裂**：

1. **一份 `docs/PRODUCT.md` + Directory-as-Product**：
   - 把产品定位、核心模块、交互铁律、明确不做什么（Non-goals）和核心领域术语内聚在一份 `docs/PRODUCT.md` 中，避免 Agent 为了改一个字段去跨 5 份碎文档（`PRODUCT` / `DOMAIN` / `DATA_PROTOCOL` / `TERMS`）对齐。
   - 前后端代码目录直接 1:1 映射 `PRODUCT.md` 中的顶层模块名（例如产品分 4 个 Tab，后端包与前端页面目录就叫这 4 个名字），让人和 Agent 零翻译成本定位代码。
2. **讨论完直接落决策（ADR）并实施，不写过渡性 `RFC`**：
   - 方案推演在对话/Plan 模式中完成；一旦明确，直接将选型理由与淘汰方案写入 `ARCHITECTURE.md`（或 `docs/adr/`）并立即改代码。未想清楚的方案不落盘。
3. **原型即产品（Prototype-as-Production）与契约代码化（Schema-as-Contract）**：
   - 当项目已有高保真可交互原型或前端样式系统（`styles.css`）时，直接以样式代码和组件作为唯一视觉真源，不再维护文字版 `DESIGN.md`；当生产前端（如 `web/`）已 1:1 承接原型后，直接在生产前端上迭代，静态原型目录即可功成身退。
   - 前后端数据结构由单一代码真源（如 `schema.py` → OpenAPI → `openapi-typescript`）自动导出生成，不手写易过期的接口协议文档。

## Mono-repo 的继承与自治

Mono-repo 的核心是**防止规则重复与跨模块越权**：

- **仓库层（根 `AGENTS.md` 与 `docs/ARCHITECTURE.md`）**：负责子项目集合、允许的依赖方向、跨模块验证命令和共同部署约束。
- **模块层（子目录 `AGENTS.md`）**：默认继承根入口约束。只有当某模块有独立的公共 API、特殊红线或独立交接节奏时，才建立模块的 `AGENTS.md`，且不重复抄写根级规则。
- **不假设自动加载**：不同 Agent 宿主对子目录指令的自动加载行为不同。根 `AGENTS.md` 必须提供清晰的模块路由表，引导跨模块任务显式读取所有受影响模块的契约。

## 规则演化的三阶漏斗（`LESSONS.md` → 正式规则）

踩坑经验不能永远堆积在 `LESSONS.md` 里变成没人读的长文，也不能一拍脑袋就写进全局死规矩：

```text
真实失败事件
  ↓ 记录证据、根因与候选规则
docs/LESSONS.md（待验证缓冲池）
  ↓ 同一模式重复出现 3 次，或单次造成严重事故 → 触发人审议
按所有者晋升并删除 LESSONS 正文（只留指向正式规则的链接）：
  ├── 属于单模块接口/实现约束 → 晋升至模块契约或 Linter/测试守卫
  ├── 属于本项目全局边界     → 晋升至根 AGENTS.md 或 ARCHITECTURE.md
  └── 属于跨项目通用工作方法 → 晋升至对应 Skill（如 engineering-discipline）
```

**最高级的规则晋升是变成自动化检查（Linter / Test / CI 门禁）**；能用确定性脚本拦住的错误，不靠文档叮嘱。
